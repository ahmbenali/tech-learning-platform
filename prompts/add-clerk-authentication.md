# Add Clerk Authentication

## Goal

Set up Clerk authentication in the existing Next.js 16 App Router project using the Clerk CLI, linked to Clerk application `app_3IZnf3K7VH4JVUniAEXA2SBN82T`, and expose clear sign-in, sign-up, and signed-in user controls in the existing Vertex navigation.

## Skills and guidance read

- `clerk`: routed the task to setup and CLI operations.
- `clerk-setup`: use `@clerk/nextjs`, keep `ClerkProvider` inside `<body>`, and keep secret configuration server-only.
- `clerk-cli`: use the CLI as the source of truth, authenticate/link explicitly, run `doctor`, and avoid printing secrets.
- Repository `AGENTS.md`: create this prompt before implementation, preserve server/client boundaries, and run the required checks.
- Next.js project instructions: inspect the installed Next.js 16 documentation before editing Next.js integration files.

## Existing code inspected

- `package.json`: Next.js `16.3.3`, React `19.2.8`, Bun lockfile; no Clerk package or auth library.
- `app/layout.tsx`: root layout currently renders children directly inside `<body>`.
- `app/page.tsx`: public Vertex home page with a header containing navigation, notifications, and a placeholder profile button.
- `app/globals.css`: existing Vertex design-system and home-page styles; reuse these patterns and avoid unrelated visual changes.
- No `middleware.ts`, `proxy.ts`, or `components.json` exists.
- Working tree contains existing untracked design/prompt files; do not modify unrelated work.

## Decisions and assumptions

- Keep the home page public.
- Use Clerk's current Next.js SDK, installed as `@clerk/nextjs` by the CLI.
- Use Clerk's hosted/prebuilt controls rather than inventing a custom auth flow.
- Preserve the existing placeholder notification behavior; replace the placeholder profile control with Clerk's `UserButton` when signed in.
- Show `SignInButton` and `SignUpButton` when signed out, and `UserButton` when signed in.
- Use Clerk's CLI to write environment configuration; never print or commit secret values.
- Do not add route protection beyond the default integration because no private Vertex feature is implemented yet.

## Implementation requirements

1. Check the Clerk CLI on the host. Install/update it only if needed, then authenticate with `clerk auth login` as required by the pasted setup request.
2. Initialize the existing project with:
   `clerk init --app app_3IZnf3K7VH4JVUniAEXA2SBN82T`
   Do not scaffold a new app or pass framework/package-manager overrides.
3. Verify the generated integration uses `@clerk/nextjs`, writes keys to an ignored local env file, and does not expose `CLERK_SECRET_KEY` to client code.
4. For Next.js 16, inspect the installed Next.js docs and verify the generated `proxy.ts`/middleware integration. If a Clerk auto-proxy matcher is required by the project’s installed integration, ensure `'/__clerk/:path*'` appears once after the API/TRPC matcher.
5. Update `app/layout.tsx` with `ClerkProvider` inside `<body>`.
6. Update the existing header in `app/page.tsx` with accessible Clerk auth controls, preserving the current Vertex layout and styling as closely as possible.
7. If the CLI creates sign-in/sign-up routes, keep them. If it does not and the generated controls require routes, add the minimal App Router routes using Clerk's documented components.
8. Do not read or print existing `.env*` contents. If required keys are missing after CLI setup, stop and report that the user must provide them.
9. Run `clerk doctor`, type checking, linting, a production build, and start the dev server long enough to verify it launches.

## Security considerations

- `CLERK_SECRET_KEY` must remain server-only and must not appear in client components, public env variables, committed files, or tool output.
- Only `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` may be exposed to the browser.
- Keep the home route public and do not add broad authentication middleware that blocks static assets or public routes.
- Avoid destructive CLI flags such as `--fresh`.
- Do not modify unrelated user changes in the working tree.

- `app/layout.tsx`.
- `app/page.tsx`.

## Acceptance criteria

- Clerk SDK is installed and the project is linked to the specified Clerk app.
- `ClerkProvider` is inside `<body>` in the root layout.
- The public home page still renders.
- Signed-out users see usable sign-in and sign-up actions.
- Signed-in users see a working Clerk user control.
- The Next.js proxy/middleware matcher is valid for the installed Next.js version and Clerk integration.
- `clerk doctor` reports no actionable setup failures.
- Type check, lint, and production build complete successfully.
- The dev server starts successfully.
